# Первый коммит и публикация на GitHub (Windows)

Инструкция для публикации **JetSport FT-10C Sync v0.5.3.27** из подготовленного архива. Она рассчитана на PowerShell и предполагает, что Git установлен.

> Перед публикацией проверьте `LICENSE`: замените строку copyright на корректного владельца авторских прав. Также убедитесь, что все сторонние зависимости и включённые файлы допускают публикацию.

## 1. Подготовить папку исходников

1. Скачайте архив `JetSport_FT10C_Sync_v0.5.3.27_github_infrastructure_candidate.zip`.
2. Распакуйте его в отдельную папку, например `E:\Projects\JetSport_FT10C_Sync`.
3. Не добавляйте в папку APK, логи с личными данными, ключи подписи, `local.properties`, IDE-кеши или другие локальные файлы.
4. Откройте PowerShell **в корне проекта** — там, где находятся `settings.gradle.kts`, `README.md` и `app/`.

## 2. Проверить Git и исходную папку

```powershell
git --version
Get-ChildItem
```

Если Git установлен, и вы в корне нужного проекта, начните репозиторий:


```powershell
git init
git branch -M main
git status --short
```

## 3. Проверить исключения `.gitignore`

Перед добавлением файлов убедитесь, что локальные файлы не попадут в репозиторий. Проверьте статус и список игнорируемых файлов:


```powershell
git status --short
git status --ignored --short
```

В частности, **не публикуйте** ключи подписи, `local.properties`, личные журналы, дампы BLE с идентификаторами устройств, APK/AAB, `build/` и `.gradle/`.

## 4. Подготовить первый коммит

```powershell
git add .
git status
git diff --cached --stat
git diff --cached --name-only
```

Внимательно просмотрите staged-файлы. Если что-то лишнее уже добавлено в индекс, удалите его из индекса (файл на диске останется):

```powershell
git restore --staged -- путь/к/файлу
```

Когда список выглядит корректно:

```powershell
git commit -m "Initial public source release v0.5.3.27"
```

## 5. Создать пустой репозиторий на GitHub

На GitHub создайте новый репозиторий с подходящим названием, например `JetSport-FT10C-Sync`.

Для первого push **не** отмечайте создание README, `.gitignore` или License на стороне GitHub — эти файлы уже есть в локальном проекте. Не выбирайте шаблонный README, чтобы избежать конфликтующей истории.

Скопируйте URL созданного репозитория (HTTPS или SSH). В следующих командаах замените placeholder на свой адрес:


```powershell
git remote add origin <URL_ВАШЕГО_РЕПОЗИТОРИЯ>
git remote -v
git push -u origin main
```

## 6. Создать тег исходного checkpoint

Тег обозначает именно этот проверенный исходный checkpoint, а не автоматически подтверждает выпуск APK:


```powershell
git tag -a v0.5.3.27 -m "Source checkpoint v0.5.3.27"
git push origin v0.5.3.27
```

## 7. Финальная проверка

```powershell
git status
git log --oneline --decorate -1
git tag --list
```

Ожидаемое состояние после успешной публикации: рабочая папка чистая, первый коммит виден в истории, ветка `main` опубликована, а тег `v0.5.3.27` присутствует локально и на GitHub.

## Важное замечание о сборке

В рамках подготовки публикационного архива проверялась целостность ZIP и состав файлов. **Android-сборка из этого точного архива здесь не выполнялась.** Перед выпуском APK рекомендуется открыть именно эту распакованную копию проекта в Android Studio, собрать и протестировать её, затем только решать, публиковать ли APK как GitHub Release.

Если GitHub-репозиторий уже создан или в нём есть коммиты, не используйте эти команды вслепую — сначала проверьте историю и remote, чтобы избежать конфликтов.
